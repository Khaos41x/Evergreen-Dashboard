# Evergreen Vision / Economy — diagnóstico e contrato

2026-10-29. Extensão local sobre World R1. Cadastro confirmado pelo usuário: somente por convite da empresa. O nome/cargo solicitado é dado de perfil, separado de papéis e de permissões financeiras. O fallback local João será substituído por perfil pessoal editável/identificação Você; dados antigos não serão apagados.

Vision é a porta visual, com UM cofre físico interativo. Nenhum distrito financeiro, saldo, gráfico ou dashboard na cena. O cofre abre por uma animação breve e navega para /economy; movimento reduzido elimina espera. Hover/foco identifica Evergreen Economy. Um botão HTML equivalente funciona por teclado e sem WebGL. /vision volta à cena. Rotas usam History API e conservam sessão/workspace; voltar do navegador funciona sem biblioteca extra.

Economy é uma página2D independente com Visão Geral, Empresas, Cofres, Movimentações, Relatórios e Planejamento. Reutiliza cliente Supabase, tokens visuais e controles nativos; não carrega Three. Não há dados demonstrativos no produto. Sem login/workspace/permissão, apresenta o estado real de acesso, nunca saldos fictícios. Valores manuais são identificados como registros internos, sem conexão bancária.

Financeiro: cada empresa pertence ao workspace e possui membros financeiros explícitos admin/editor/viewer. Ser membro da holding ou declarar um cargo não dá acesso financeiro. Owner do workspace pode cadastrar empresa e torna-se seu admin financeiro; conceder acesso a outro colega é ação explícita. Todas as tabelas têm RLS e escritas financeiras ocorrem via RPC transacional. Auditoria financeira não vai para a timeline geral, que é visível a colegas sem acesso financeiro.

Livro-caixa em centavos inteiros bigint, valores transportados como strings e BigInt no cliente. Moedas não são somadas entre si e transferências de moedas diferentes são rejeitadas. Cada transferência gera duas pernas opostas no mesmo evento/transação, sob locks de contas; consolidar as duas empresas tem efeito líquido zero. Só uma empresa autorizada mostra sua própria perna. Lançamentos são imutáveis; correções são estornos, não exclusões. Requisições têm UUID idempotente. Reservas são contas vinculadas um-a-um a metas, evitando contar reserva duas vezes. Orçamentos/projeções são planejamento explicitamente estimado e nunca misturados aos valores realizados.

Snapshot calcula saldos e agregados no servidor sobre todos os lançamentos autorizados; histórico é paginado separadamente. Não usar apenas uma página de movimentos para exibir saldo total. Valores e limites são validados também no SQL. Nenhum câmbio, recomendação de investimento, integração bancária ou transação bancária é implementado.

Migrações anteriores e primeiro responsável continuam pendentes no Supabase hospedado. Esta etapa cria fonte/migrações/testes locais; não aplica nem publica alterações de produção. Validação PGlite/REST de fixture deve ficar separada da validação real. Metas: transferência não altera consolidado, nenhum vazamento entre empresas/workspaces, viewer não escreve, retry não duplica, estorno só uma vez, dinheiro decimal exato, perfil persistente e cargo não eleva papel, rota acessível e fluxos em478/390/1440px.
